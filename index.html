EnderBeam

Hosted websites for Minecraft servers. Owners install a plugin, drag modules onto a page, and publish a site that connects to their server, Discord, and store.

Visit enderbeam.com ↗

How it works

There are two apps: an editor where owners build their site, and a renderer that shows the finished site to visitors. Both read the same site schema and use the same set of modules, so a new module shows up in both at once. A Spring Boot backend stores every site in PostgreSQL, syncs live edits over WebSockets, and receives data from each server's plugin.

Hard problems

  • Cheap multi-tenant hosting. One renderer build and one backend serve every site. A new customer is simply a database row instead of a new app.
  • Keeping three apps in sync. The editor, renderer, and backend share one versioned schema. Older sites upgrade automatically when they load.
  • Editing together. Several people can edit a site at once, with drafts, publishing, and undo.
  • Safe deploys. Every release is tested against a copy of the production schema, then goes live with no downtime.

GardensMC

A survival Minecraft community I run, with 736 registered players and 300+ active each month across Java and Bedrock. Nearly all of its gameplay runs on four plugins I wrote.

Visit gardensmc.com ↗
Screenshot coming soon

Architecture

Each plugin is its own Gradle project and jar. They talk through small public APIs, so one can ship without redeploying the others.

Engineering highlights

  • Storage without a database. Furniture state lives in each chunk’s own data, behind a cache that loads with the chunk. World generation used to re-encode a chunk’s whole store for every block placed, which was quadratic. Buffering per chunk and writing once made it linear.
  • Monthly world resets with backpressure. Replacement worlds are generated ahead of time, one at a time. Generation pauses when memory, loaded chunks, or pending furniture get too high, and resumes when they drop. A reset swaps in a ready world, archives the old one to S3, and warns staff when fewer than three are left.
  • Keeping the main thread free. Minecraft runs game logic on a single thread, so every MySQL call goes through async Caffeine caches. Expensive reads like the quest leaderboard are cached for minutes instead of queried on every menu open.
  • Bedrock support. Key menus switch to native Bedrock forms for Bedrock players. A GeyserMC fork renders custom blocks for them, with changes kept in a thin shim so upstream releases merge cleanly.
  • Tested and automated. 36 test classes cover the economy, quests, crop growth, furniture rotation, and more. CI runs on every push, and the Geyser fork deploys itself to the server.

SeamlessPortals

See-through portals for Minecraft. Nether portals, End portals, and custom portals show the world on the other side live, and you cross by just walking through, with no loading screen. Riding, flying, and leashed animals cross too. It runs as a client-side Fabric mod, with a Paper plugin companion for multiplayer servers.

Screenshot coming soon

Highlights

  • Live rendering of the far side with custom GLSL shaders, on the client.
  • One codebase, two platforms. A Fabric mod (client and server) and a Paper plugin share common code. Players without the mod still see and use portals as normal.
  • Custom portals of any size and shape, linked within or across worlds, through an admin command and a wand.
