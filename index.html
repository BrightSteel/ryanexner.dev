EnderBeam

Hosted, branded websites for Minecraft servers. Owners install a plugin, drag modules onto a page, and get a live site that ties into their server, their Discord and their store.

Visit enderbeam.com ↗

How it works

Two apps share one module registry and one site schema. The creator app edits a site's schema; the tenant runtime, a single static build, looks up the schema by hostname and renders the same modules for visitors. A Spring Boot backend stores every tenant's site in PostgreSQL, handles live collaboration over WebSockets, and takes data that each server's plugin pushes in. Adding a module to the registry once makes it available in the editor and on every live site.

Hard problems

  • Multi-tenant hosting that stays cheap. One static runtime build and one backend serve every customer site. Each site's schema is resolved by hostname, so a new tenant is a database row, not a new server.
  • Keeping three apps in sync. A versioned JSON site schema with Zod validation is the contract between the editor, the runtime and the backend. Old schemas migrate on read, and stored rows migrate through Flyway.
  • Several people editing at once. Live collaboration runs over WebSockets, with drafts, publishing, and undo/redo.
  • Deploying without breaking live sites. CI runs type checks, tests and a migration rehearsal against the production schema, then deploys blue/green.

GardensMC

A survival Minecraft community I run. Most of its gameplay comes from a suite of plugins I wrote, which share APIs and build on each other the way a small set of services would.

Visit gardensmc.com ↗
Screenshot coming soon

How the plugins fit together

GardensFurniture is the foundation: a framework for custom blocks that the other plugins build on. GardensEnchants and GardensCrops sit on top of it, and GardensPlayers ties everything together into the player-facing economy, quests and shops. Each plugin exposes a small API the others call, so they can ship independently.

Highlights

  • Resource worlds that reset themselves. GardensPlayers generates fresh resource worlds every month and archives the old ones to S3-compatible storage with multipart uploads.
  • Fast player data. Player data lives in MySQL through HikariCP, with a Caffeine cache in front for hot reads.
  • Bedrock players see everything. I maintain a fork of GeyserMC, the Bedrock-to-Java proxy, so custom blocks and furniture render for Bedrock players too. Fork changes sit in a thin shim so upstream releases merge cleanly.
  • Tested and automated. Unit tests and GitHub Actions CI run across the suite, and the Geyser fork deploys itself to the server.

SeamlessPortals

See-through portals for Minecraft. Nether portals, End portals and custom portals show the world on the other side live, and you cross by just walking through, with no loading screen. Riding, flying and leashed animals cross too.

Screenshot coming soon

Highlights

  • Live rendering of the far side with custom GLSL shaders, on the client.
  • One codebase, two platforms. A Fabric mod (client and server) and a Paper plugin share common code. Players without the mod still see and use portals as normal.
  • Custom portals of any size and shape, linked within or across worlds, through an admin command and a wand.
